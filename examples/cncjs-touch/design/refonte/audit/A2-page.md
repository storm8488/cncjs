## Constats

### A2-1 — Confirmer s'active sur un dépassement de course prouvé
- **Gravité** : sécurité machine. **Journal** : T2 (et T3). **Décision** : D1.
- **Phrase** : le dialogue de démarrage affiche « HORS COURSE » pour un axe vérifié, mais la case cochée suffit à activer Confirmer, et le nonce part au serveur.
- **Scénario** : machine référencée, `programCheck` du ticket avec `Z: outside` (cas de T2, Z −130,76 → −105 pour une course de −130 à 0) ; Démarrer…, puis case cochée → `#job-confirm.disabled === false` → clic → `POST {action:'start'}` envoyé.
- **Preuve** : test `examples/cncjs-touch/test-bughunt-A2-1.cjs`, qui affiche « Confirmer enabled with a proven outside verdict: true · start requests sent: 1 ». Chemin : `job-controls.js:559` (le contrôle n'est qu'affiché) → `job-controls.js:584` (`disabled=!this.checked||!confirmable()`) → `confirmable()` / `ticketAllowed()` `job-controls.js:282-293` (aucune lecture du verdict) → `job-controls.js:589` (envoi).
- **Correction proposée** : avec D1, le serveur refuse le ticket (A1). Côté page : un verdict `outside` sur un axe vérifiable n'active jamais Confirmer par la case seule. La dérogation est un second geste distinct, journalisé, avec la cause chiffrée et le remède. Un verdict `unknown` reste un avertissement lisible.
- **Fichiers** : `touch/job-controls.js`, `touch/program-check-view.js` (et le serveur `job-service.js` pour D1).

### A2-2 — Le contrôle des courses lit le WCO rapporté (0 après la prise d'origine) : faux « hors course » (T3) et faux « dans la course »
- **Gravité** : sécurité machine (cas inverse) ; bloquant (T3). **Journal** : T3, T2. **Décision** : D2 ; pistes 2 et 3 (A1).
- **Phrase** : juste après `$H` sur la LUNYEE (MPos 0, `WCO:0` rapporté, G54 toujours dans `$#`), le contrôle donne « X inconnu · Y inconnu · Z hors course » pour une poche qui tient. Un programme qui descend réellement sous la course peut au contraire être déclaré « Z validé ».
- **Scénario** : réglages LUNYEE (`$23=3`, `$130-132` 408 / 396 / 130), `mpos = wpos = 0`, `$#` G54 = X150 Y120 Z−100. (1) Poche Z +5 → −10 : réellement −110 → −95, donc dans la course ; verdict `X unknown · Y unknown · Z outside` (« Hors course Z : -10 → 5 mm machine »), soit le dialogue rouge de T3. (2) Programme Z 0 → −35 : réellement −135, sous −130, ce qui donne `ALARM:2` comme dans T2 ; verdict « Z validated ».
- **Preuve** : test Jest `src/server/services/touch/__tests__/bughunt-A2-3.test.js` (2 échecs ; les journaux du test donnent les verdicts). Chemin : `job-service.js:1353-1376` (`machineForCheck` : mpos / wpos rapportés, ni `homeMpos` ni recoupement avec `$#`) → `program-check.js:519-525` (décalage = mpos − wpos) → `program-check.js:569-572` (axe à bit `$23` : toujours `unknown`).
- **Correction proposée** : côté serveur (A1, D2). Recouper le décalage actif avec `$#` du repère actif. Ni départ, ni palpage, ni reprise tant que ce n'est pas prouvé. Lever l'inconnu `$23` quand la prise d'origine a appris la convention (piste 3). Côté page : rien à changer, sauf A2-1.
- **Fichiers** : `src/server/services/touch/job-service.js`, `program-check.js`. Recouvre les pistes 2 et 3 d'A1 : à dédoublonner en phase 2.

### A2-3 — Sonde : refus écrit au-dessus d'un « Palper… » resté actif ; un deuxième toucher ne change rien à l'écran
- **Gravité** : à corriger. **Journal** : T6 (« j'ai cliqué, rien ne se passe »), T7.
- **Phrase** : un refus de préparation (ici `ETOUCH_PROBE_TRAVEL`, le cas de T7) s'écrit en petit dans `#probe-message`, au-dessus de Palper…, qui reste actif. Un nouveau toucher efface la ligne puis la réécrit à l'identique : une fois la réponse arrivée, l'écran est exactement le même qu'avant.
- **Scénario** : XYZ, profil complet, machine prête ; Palper… → refus `ETOUCH_PROBE_TRAVEL` ; Palper… encore → même refus → photographie de l'écran identique (deux requêtes envoyées). Le « Demande envoyée… » et le refus vont aussi dans `#job-feedback`, qui n'est visible que sur Fichiers et Suivi.
- **Preuve** : test `test-bughunt-A2-4.cjs` partie (a). Chemin : `probe-ui.js:207-213` (`realRefusal=''`, puis le même texte) → `probe-ui.js:192-199` (`launch.ready` reste vrai, `#probe-message` en dessous de la phase).
- **Correction proposée** : composant « refus avec son bouton » (L1). Le refus s'affiche à côté du bouton, avec l'heure ou un compteur de nouvelle tentative et le remède sur place. Pour `ETOUCH_PROBE_TRAVEL`, c'est le dessin de la zone de départ et un renvoi vers les déplacements. Palper… ne reste pas l'action principale tant que la cause n'a pas changé.
- **Fichiers** : `touch/probe-ui.js`, `touch/probe-real.js`.

### A2-4 — « Diagnostic de l'entrée » ne suit pas le test du contact que le serveur exige
- **Gravité** : à corriger. **Journal** : T6 (« toujours grisé »), T9. **Décision** : D4 (diagnostic guidé).
- **Phrase** : Palper… est grisé par « Test du contact à faire… Ouvrez Diagnostic de l'entrée. », mais cet écran n'affiche ni les étapes du test (libre → contact → libre), ni s'il est fait. Il dit même : « Ce diagnostic ne valide ni le câblage ni un cycle de palpage », alors que c'est précisément le test que le serveur attend.
- **Scénario** : `blockProbeReason` = test à faire, `probeInput.test.done=false`, contact vu ; puis test fait (`test.done=true`). Aucun texte de l'écran ne change pour le dire (seul le mot de l'état de l'entrée change). Avec une broche qui met l'outil à la masse (T9), le test ne peut jamais aboutir, et rien ne le suggère.
- **Preuve** : test `test-bughunt-A2-4.cjs` partie (b). Chemin : `probe-ui.js:326` (étapes masquées sur la page réelle) ; `probe-ui.js:350` (`probeInput.test` lu seulement pour la signature de rendu) ; `probe-ui.js:183` (texte « ne valide ni… »).
- **Correction proposée** : les trois étapes, avec l'état venu de `probeInput.test`, en vert quand c'est fait. Un retour « Palper… » quand le test est fait. Un contact permanent fait apparaître la cause probable (pince, broche à débrancher).
- **Fichiers** : `touch/probe-ui.js`, `touch/probe-model.js`.

### A2-5 — La carte « Zéro Z avec une plaque » disparaît de Suivi sans raison

- **Scénario** : `cnc-job-status` avec `canZeroZ:true` → carte visible ; puis `canZeroZ:false` et sa raison → carte masquée, aucun texte de Suivi ne contient la raison. Sur Sonde, « Zéro Z avec plaque → Suivi » est grisé, avec la raison seulement dans `title`, qu'un écran tactile n'affiche pas.

- **Correction proposée** : la carte reste, son bouton est grisé avec la raison en une phrase et le remède (diagnostic de la sonde, Relire…). Le dernier résultat reste visible.
- **Fichiers** : `touch/job-resume.js`, `touch/probe-ui.js`.

### A2-7 — Après un redémarrage de CNCjs en alarme, « Relire les réglages » est offert grisé, et la sortie est une chaîne de trois commandes en texte

### A2-8 — Des refus de préparation invisibles là où l'on a touché (assistant, bandeau, macros, opération en cours)

### A2-14 — Le pavé numérique ne peut pas vider un champ
